# Local Environment Notes

Issues encountered setting up this machine, and how they were resolved. Recorded because they
are environment-specific and would otherwise look like project bugs.

## 1. Maven could not reach Maven Central — `PKIX path building failed`

**Symptom.** Every Maven download failed with:

```
Could not transfer artifact org.springframework.boot:spring-boot-starter-parent:pom:4.1.1
(certificate_unknown) PKIX path building failed:
unable to find valid certification path to requested target
```

`curl` to the same URL worked, which is what made it confusing.

**Cause.** Avast Antivirus performs HTTPS interception. Inspecting the chain shows the
certificate is re-issued locally:

```
$ openssl s_client -connect repo.maven.apache.org:443 -servername repo.maven.apache.org
 0 s:CN=repo.maven.apache.org
   i:OU=generated by Avast Antivirus for SSL/TLS scanning, O=Avast Web/Mail Shield, ...
```

Avast's root CA is installed in the **Windows** certificate store, so Windows-native tools
(curl, browsers) trust it. The JDK ships its own `cacerts` truststore, which does not contain
it, so every Java-based tool — Maven, Gradle, anything using `HttpsURLConnection` — fails.

**Workaround used during development.** Point the JVM at the Windows root store, which already
contains the Avast CA. Certificate verification stays fully enabled:

```bash
MAVEN_OPTS="-Djavax.net.ssl.trustStoreType=Windows-ROOT" mvn clean verify
```

**Permanent fixes**, in order of preference:

1. **Import the Avast root into the JDK truststore** (needs an Administrator shell):
   ```powershell
   $cert = Get-ChildItem Cert:\LocalMachine\Root |
       Where-Object { $_.Subject -like "*Avast Web/Mail Shield Root*" }
   Export-Certificate -Cert $cert -FilePath "$env:TEMP\avast-root.cer"
   & "$env:JAVA_HOME\bin\keytool" -importcert -trustcacerts -noprompt `
       -alias avast-root -file "$env:TEMP\avast-root.cer" `
       -keystore "$env:JAVA_HOME\lib\security\cacerts" -storepass changeit
   ```
   Fixes every Java tool at once, including IntelliJ's bundled Maven.

2. **Set `MAVEN_OPTS` permanently** for the user (no Administrator rights needed):
   ```powershell
   [Environment]::SetEnvironmentVariable(
       "MAVEN_OPTS", "-Djavax.net.ssl.trustStoreType=Windows-ROOT", "User")
   ```
   Fixes Maven only; IntelliJ needs the same flag added under its Maven VM options.

3. **Disable Avast's HTTPS scanning**
   (*Menu → Settings → Protection → Core Shields → Web Shield → uncheck "Enable HTTPS
   scanning"*). Removes the interception entirely.

> **This affects only this machine.** No workaround is committed to the repository — a grader on
> a machine without TLS interception builds the project with a plain `mvn clean verify`.

## 2. Intermittent `user-mapped section open` during downloads

**Symptom.** A Maven build fails once with:

```
The requested operation cannot be performed on a file with a user-mapped section open
```

**Cause.** Avast's real-time file shield holds a lock on a freshly written `.m2` artifact while
Maven tries to move it.

**Fix.** Re-run the build; it succeeds on the second attempt. Adding `C:\Users\<user>\.m2` to
Avast's exclusion list removes the flakiness permanently.

## 3. Spring Boot 4 migration notes

Two Boot 4 changes surfaced during scaffolding and are worth knowing, since most online examples
still target Boot 3:

| Change | Effect |
|--------|--------|
| **Jackson 3** (`tools.jackson.*`) replaces Jackson 2 | `spring.jackson.serialization.write-dates-as-timestamps` no longer exists — `WRITE_DATES_AS_TIMESTAMPS` moved off `SerializationFeature`. Jackson 3 already defaults to ISO-8601 for `java.time`, so the property was simply removed. |
| **Autoconfiguration split into per-technology modules** | `org.flywaydb:flyway-core` on its own is inert. `org.springframework.boot:spring-boot-flyway` must be added for Flyway to run at startup. Flyway migrations silently did not execute until this was added — the application started perfectly with an empty database. |

## 4. GitHub push protection rejected a test fixture

**Symptom.** A push was refused:

```
remote: - GITHUB PUSH PROTECTION
remote:     - Push cannot contain secrets
remote:       —— Stripe API Key ——
```

**Cause.** A unit test used Stripe's published documentation key as a realistic-looking
credential. It is not a live secret, but it matches Stripe's `sk_live_` key format exactly, which
is what the scanner detects. The literal value is deliberately not reproduced here — quoting it
in this file is what caused the *second* rejected push.

**Fix.** Replaced the fixture with `dummy-provider-credential-ABCD`, which cannot be mistaken for
any provider's key format. GitHub offers an "allow this secret" link; it was not used. Suppressing
a detector so a test can keep using a realistic key teaches the repository to ignore exactly the
signal it exists to produce — and the fixture's realism was buying nothing.

## 5. A flaky test caused by base64 canonicalisation

**Symptom.** `AuthenticationIT.tamperedTokenIsRejected` passed repeatedly, then failed once with
the tampered token being accepted as valid.

**Cause.** The test tampered with a JWT by flipping the **final** character of the signature. An
HS256 signature is 32 bytes, encoded as 43 base64url characters: the first 42 carry 252 bits and
the last carries only the remaining 4. Several distinct final characters therefore decode to the
same 32 bytes, so the "tampered" signature was sometimes byte-identical to the real one and the
token was legitimately valid.

**Fix.** Tamper with a character in the middle of the payload segment instead, which always
changes the signed content. Verified deterministic across repeated runs.

**Worth noting** because the failure looked like a security bug in token verification and was in
fact a bug in the test. The verification code was correct throughout.
